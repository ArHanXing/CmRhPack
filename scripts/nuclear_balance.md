## 0. 结论速览

| 项 | 结论 |

| 反应堆类型 | 任意长宽、可多层堆叠的矩形多方块，最大 64 |

## 1. 反应堆的真实模型

### 1.1 能量与热量（字节码验证）

`ReactorControllerBlockEntity.serverTick()` 里的实际运算：

```java
// 能量
energyStorage.insertIgnoringLimit(RF_PER_PULSE * pulses * reactorStackHeight)

// 热量（整数除法）
heat = (pulses / 2) * pulses + 4
```

展开成公式：

```
P      = 内部脉冲 + 外部脉冲
内部脉冲：单联 1 ／ 双联 4 ／ 四联 12
外部脉冲：相邻燃料棒或中子反射器送来（双联送 2、四联送 4）

能量 = P × 64 RF/t × 堆叠高度        ← 线性
热量 = ⌊P/2⌋ × P + 4                 ← 二次
耗料 = 棒数 单位/tick × 堆叠高度
```

### 1.2 辅助组件

| 组件 | 公式 |
|---|---|
| 散热口 | `min(邻温/100 + 4, 邻温)` |
| 热量吸收器 | 每面 16（最多 4 面 = 64），需持续吃冰/浮冰/蓝冰 |
| 热量管道 | `温差/4 + 10` |
| 能量端口 | 每端口 ≤ **32768 RF/t**（配置已从默认 25000 提高） |
| 熔毁 | 热 > 2000 且持续 600 tick → 爆炸（`safeMode = false`） |
| 警告 | 热的 85%（= 1700） |

### 1.3 配置现状（`config/oritech-common.toml`）

| 配置项 | 默认 | 本包 |
|---|---|---|
| `rfPerPulse` | 64 | 64 |
| `maxHeat` | 2000 | 2000 |
| `reactorMaxEnergyOutput` | 25000 | **32768** |
| `reactorMaxEnergyStored` | 50000000 | **67108864** |
| `ventBaseRate` / `ventRelativeRate` | 4 / 100 | 4 / 100 |
| `absorberRate` | 16 | 16 |
| `safeMode` | — | **false**（真的会炸） |

## 2. 硬约束：反应堆不产出物品

反应堆配方只有 `{type, time, results, ingredients}`，其中 **`results` 不生效** —— 反应堆是纯"燃料 → 能量"的黑箱。

**后果**：经典的核燃料循环在本版本**不可实现**：

```
❌ 乏燃料 → 后处理 → 钚 → MOX        （无法取出任何物品）
❌ 裂变产物 → 玻璃固化 / 同位素分离
❌ 嬗变增殖
```

⇒ 本包**不能**做"燃料循环"这条纵深。核裂变的全部内容只能是：

- 燃料制造（已有：空棒 + 粉尘）
- 堆芯设计（玩家自行钻研，这是 Oritech 的乐趣所在）
- 热管理（散热口/管道/吸收器）
- 燃料梯级（铀 → 钍 → MOX → 超能硅岩）

**平衡杠杆因此只剩两个**：① 配方 `time`（本次改的）② 燃料制造成本（见 §5）。

## 3. 设计张力：想省燃料就要指数级散热

| P | RF/t | 热/tick | 热/电比 | 1000°C 所需散热口 | 占地 |
|---|---|---|---|---|---|
| 1（单联裸棒） | 64 | 4 | 0.063 | 1 | 极小 |
| 12（四联裸棒） | 768 | 76 | 0.099 | 6 | 小 |
| 28（四联 + 4 邻） | 1792 | 396 | 0.221 | 29 | 中 |
| 36（四联 + 6 邻） | 2304 | 652 | 0.283 | 47 | 大 |

同时，**外部脉冲是纯赚**（不多耗料）：

| 棒型 | 内部脉冲 | 棒数 | EU / 单位容量 |
|---|---|---|---|
| 单联 | 1 | 1 | 64 |
| 双联 | 4 | 2 | 128 |
| 四联 | 12 | 4 | 192 |
| 四联 + 6 邻 | 36 | 4 | **576** |

⇒ 反应堆"好玩"就建立在 **燃料密度 ↔ 散热成本** 的取舍上。高功率堆会迅速变成一座散热塔。

## 4. 数值设计

### 4.1 参考堆

平衡讨论需要一把尺子。本报告取：

> **参考堆 R**：四联棒 + 6 个四联邻棒 ⇒ **P = 36**，单根 **2304 RF/t**，**652 热/tick**

- 单层 7 棒核心总输出 ≈ **16,128 RF/t ≈ 2A IV**
- 5 棒版本（四联 + 4 邻）≈ **8,960 RF/t ≈ 1A IV**
- 1 根四联裸棒 = 768 RF/t（0.375 A EV）

### 4.2 容量规则

**容量随棒数线性**，使任何棒型烧一颗丸的时长一致；差异只体现在能效（64/128/192 EU per 容量）：

```
单联棒容量 C  ⇔  双联棒容量 2C  ⇔  四联棒容量 4C
```

这条规则与既有的双联合成配方（`2 × 单联 → 1 × 双联`）天然吻合。

### 4.3 锚点计算

以「**四联棒烧一颗铀丸 7.5 分钟**」为基准：

```
C_uranium = 9000 tick × 4 = 36,000
每颗丸能量 = 9000 × 36 × 64 = 2.07e7 EU
1 铀矿 → T1.5 ×3 粉 → 3 颗丸 = 6.2e7 EU/矿

一个 7 棒核心（16,128 RF/t）每小时消耗：
    7 棒 × (3600 / 450 s) = 56 颗丸 = 18.7 铀矿/小时
```

⇒ **约 19 铀矿/小时 换 2A IV**，这个量级与一座中型矿场的产出匹配，既体现"核电是升级"，又不至于让铀矿变成唯一该挖的东西。

### 4.4 最终取值

| 燃料 | `time`（容量） | 四联棒燃烧 | 每颗丸能量 | 相对铀 | 定位 |
|---|---|---|---|---|---|
| 铀丸 | **36,000** | 7.5 min | 2.07e7 | 1× | T2.5 入门 |
| 双联铀 | **72,000** | 15 min | 4.15e7 | 2× | |
| 钍丸 | **72,000** | 15 min | 4.15e7 | 2× | 便宜、慢 |
| 双联钍 | **144,000** | 30 min | 8.29e7 | 4× | |
| MOX | **108,000** | 22.5 min | 6.22e7 | 3× | 高效 |
| 双联 MOX | **216,000** | 45 min | 1.24e8 | 6× | |
| 超能硅岩 | **360,000** | 75 min | 2.07e8 | 10× | T3 巅峰 |
| 双联超能硅岩 | **720,000** | 150 min | 4.15e8 | 20× | 一颗丸即可启动聚变堆（3e8） |

**旧值对照**：铀 2000 → 36000 是 **×18**。旧值下一个 7 棒核心 25 秒就要补一次料，完全不具备可用性。

### 4.5 反查公式（日后要改目标时用）

```
容量       = 目标燃烧时长(tick) × 棒数
每颗丸能量 = 目标燃烧时长 × P × 64
核心总输出 = 棒数 × P × 64
所需铀矿/小时 = 核心输出 × 3600 ÷ 每颗丸能量 × 棒数 ÷ 3
```

## 5. 待决问题：燃料制造成本

**当前成本**：
```
1 铀矿 --T1.5--> 3 铀粉 --+1 空棒(组装机)--> 3 铀燃料棒
1 空棒 = 4 × (1 亚稳板 + 1 铅板) / 4  ← 每 4 根空棒消耗 2 个板
```

在 §4.4 的取值下，**1 铀矿 ≈ 6.2e7 EU**。作为对照，本包最优石化燃料硝基碳燃油是 **244,000 EU/桶** ⇒ 1 铀矿 ≈ **255 桶燃油**。

这个倍率是否合适，取决于想要核电有多"重"。三种可选：

| 方案 | 做法 | 效果 |
|---|---|---|
| **A. 保持现状** | 不改燃料配方 | 核电极强，石化沦为前期过渡 |
| **B. 引入浓缩（推荐）** | 4~8 铀粉 --离心/化反--> 1 浓缩铀粉 → 1 燃料棒 | 1 铀矿 ≈ 0.4~0.8 颗丸，核电变成需要专门矿场的产业 |
| **C. 提高空棒成本** | 空棒改为消耗亚稳板 ×1/根 | 温和收敛，不新增物品 |

> 本报告**未改动**燃料配方，仅改 `time`。§5 需要作者决定后再执行。

## 6. 未验证项与已知缺口

### 6.1 未验证（因无法开游戏）

**热量的高度缩放存疑**。字节码里：

```java
// 能量、耗料都显式 × 高度
RF_PER_PULSE * pulses * reactorStackHeight
tryConsumeFuel(rodCount * reactorStackHeight, ...)

// 热量那三行却**没有** × 高度
heat = (pulses / 2) * pulses + 4
```

两种可能：
- **(a) 热量按列累计**（`componentHeats` 是 `HashMap<Vector2i, Integer>`，逐层累加到同一 (x,z) 键）⇒ 行为正常，堆高不免费
- **(b) 热量真的不随高度增长** ⇒ **堆得越高热/电比越好**，是个显著的最优解甚至漏洞

**必须进游戏实测**：同一二维布局做 1 高 vs 10 高，看总热是否 ×10。若是 (b)，§4 的数值需要按"最佳高度"重算，而且应当考虑限制堆高或修正公式。

### 6.2 材料可达性缺口

| 燃料 | 原料 | 状态 |
|---|---|---|
| 铀丸 | `oritech:uranium_dust` | ✅ 10 条产出配方（T1.5 铀线） |
| MOX | `oritech:plutonium_dust` | ❌ **零产出配方** ⇒ MOX 燃料棒是死物 |
| 钍丸 | `jsonreg:thorium_dust` | ❌ **零产出配方** ⇒ 钍燃料棒是死物 |
| 超能硅岩 | `jsonreg:naquadria_dust` | ⚠️ 有 1 条产出，但上游 `raw_naquadria` 无来源 |

⇒ **八种燃料里目前只有铀真的能做出来。** 钍/MOX 需要补原料来源（钍可从既有的 `jsonreg:thorium_concentrate` 接，但那个也是零下游）。

### 6.3 OR 原版燃料已弃用

`<recipetype:oritech:reactor>.removeAll()` 之后只重建了自定义燃料棒，Oritech 自带的
`uranium_pellet` / `plutonium_pellet` / `small_*_pellet` **不再有任何反应堆配方**。

它们目前仍可由 `precision_assembly.zs` 的转换配方产出（OR 装配器配方转来的），但**产出来没有任何用途** ⇒ 死物。

建议：要么给它们一个用途（例如作为浓缩路线的中间体），要么把产出配方一并清退，避免 EMI 里出现无用的物品。

### 6.4 工具盲区

`t2.zs` 的 `_reactor()` / `_fuelrod()` 是**函数生成配方**，配方名是变量：

```zenscript
function _reactor(_recipe as string, _id as string, _time as int) as void {
    <recipetype:oritech:reactor>.addJsonRecipe(_recipe, {...});
}
```

`scripts/tools/audit_recipes.py` 的扫描正则是 `addJsonRecipe("字面量"`，因此**这 8 条反应堆配方 + 4 条燃料棒配方从未被审计覆盖**（重名、槽位越界都查不到）。

同理受影响：`t1.zs`、`t3.zs` 里的 `_smd_assembler` / `_fuelrod` 等函数。
